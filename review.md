# Duo 0.4.5 security review

> Findings F1–F6 remediated in Duo 0.4.6; see plan.md §9 and the 0.4.6 CHANGELOG entry.

Reviewed HEAD `a11516c`. The difference from `v0.4.5` contains only `docs/STATUS.md` and `plan.md`; the implementation is unchanged. This review evaluates the supported single-user, trusted-repository, unmanaged-CLI baseline.

The implementation supports many of Duo’s stated protections. One reproducible availability defect contradicts the credential scanner’s performance claim. Other findings concern inaccurate assurance levels, inconsistencies in recorded evidence, and evidence-reproduction tooling. No sandbox escape or live credential disclosure was demonstrated.

Evidence here consists of source inspection, repository fixtures and tests, historical reports in `docs/STATUS.md`, and limited read-only execution on Linux with Python 3.12.3. Three fixture checks passed: `RecordedProbeTests.test_every_tested_version_has_fixtures`, `test_copilot_help_and_config_match_required_controls`, and `test_fixtures_contain_no_credentials_or_home_paths`. The full suite was not run: this workspace is read-only and LangGraph is not installed. No authenticated reviewer calls were made. Historical live reports are identified as such, rather than represented as independently reproduced results.

## Findings, ranked by severity

### F1 — Medium: credential checking has quadratic cases within the permitted response size

**Claim:** `docs/SECURITY.md:132–133` says runtime grows linearly and adversarial inputs at the 1 MiB limit take well under a second.

**Evidence:** The OpenAI pattern at `src/duo/models.py:198` allows an unbounded token-character sequence before the required marker. For text consisting of repeated `sk-`, each possible prefix causes another scan of the remaining suffix. Direct calls to `new_secret(text, '')` took approximately 0.058, 0.230, and 0.904 seconds for 12,288, 24,576, and 49,152 bytes respectively. A 1,048,575-byte input was stopped by a five-second alarm without completing. These are synthetic strings, not credentials. The approximately fourfold increase when input doubles agrees with the repeated suffix scanning in the pattern. The full-size cost is extrapolated from this growth, not measured.

A second quadratic case exists at `models.py:206–210`: every matched occurrence performs a substring search through the current document. Repeating one synthetic GitHub-shaped token in the response, with that token appearing only at the end of an equally sized padded current document, took approximately 0.073, 0.259, 0.972, and 3.807 seconds at 128, 256, 512, and 1,024 KiB. The existing adversarial test, `tests/test_duo.py:413–431`, repeats identical known material at the beginning of the known document and does not exercise either case.

**Conditions:** The trigger is near-match text in a reviewer's `plan` or `reason`, which a malformed response or prompt-injected repository text could cause. Model output-token limits make a near-1 MiB crafted response less likely than the size checks allow. The measured tens-of-KiB cases already break the documented guarantee, and the second case also needs a large current document. Disabling web tools does not limit either case.

**Worsening factor (planned):** `plan.md` section 3 proposes scanning `--context-file` material with the same `SECRET_PATTERNS` when it is captured, before any reviewer starts. Saved logs and test output are user-supplied, are not limited by model output, and can naturally contain many `sk-`-like or token-like fragments. The defect would then affect ordinary startup, not only unusual responses.

**Impact:** A malformed or manipulated reviewer response can consume substantial CPU in Duo after the reviewer process has finished, delaying the user and holding the repository lock. The reviewer-process timeout does not bound this work. `Reviewer._review` checks the run deadline before `validate_review`, then publishes or accepts the result without another deadline check (`src/duo/workflow.py:72–77,106–138`). This is a local availability issue, not evidence of credential-filter bypass or code execution.

**Minimal remediation:** Remove repeated suffix and known-document scans while preserving the existing detection formats and already-known-value behavior. Add regression cases for repeated near-match prefixes and matches near the end of a large known document, and recheck the deadline before accepting a validated response. Retain a measured performance requirement rather than merely deleting the documentation claim. Fix this before, or together with, the `plan.md` section 3 context-file credential check, which reuses these patterns.

### F2 — Low: “Verified each run” overstates what some preflight checks establish

**Claim:** `docs/SECURITY.md:8–9` defines this label as confirming the control and stopping for an ineffective control. The writing/tool rows apply it to Codex overrides, Claude flag availability, and Copilot flags/settings (`:42–43,53–54,64–65`). README’s comparison table makes the same per-run claim in summary form (“Checked before every run and refused if missing”, `README.md:24`).

**Evidence:** `verify_controls` checks advertised option names, effective Codex feature values, the MCP listing, and Claude managed-policy metadata (`src/duo/policy.py:217–268`). Copilot checks advertised options and selected effective settings (`src/duo/copilot.py:203–245`). These are useful checks, but they do not exercise write denial, read confinement, network denial, or every tool restriction on each run. For example, Codex’s sandbox and approval values are supplied by `CLIAdapter.command` and `codex_options`; the feature-list probe does not return those values. `tests/test_policy.py:test_rejects_missing_or_ineffective_controls` verifies rejection for the specific metadata changes it simulates, not universal enforcement.

The credential context of the Codex MCP probe also needs precision. SECURITY.md says it runs “without credentials” (`:43`), but `policy.py:234–236` retains `reviewer_environment('codex', pass_env)`, including `CODEX_API_KEY` and `OPENAI_API_KEY` when set (`:54–67`). The temporary `CODEX_HOME` removes the usual stored-login location; it does not guarantee an authentication-free environment.

In the other direction, the same Codex row’s “Not verified: a deliberate write attempt” (`SECURITY.md:42`) understates the evidence. `STATUS.md:75,103,133,170,182–188` reports deterministic write-denial probes, run with Duo’s `codex_options()` and `reviewer_environment('codex')`, that failed with “Operation not permitted”, “Read-only file system”, or `EROFS` and created no files. Only the model-directed write probe went unproven (it timed out).

**Impact:** Users can mistake a successful configuration preflight for a fresh enforcement test, or misunderstand which authentication context was checked. A CLI regression could retain its advertised options without being detected by these particular probes. This finding identifies an assurance mismatch; it does not establish that any current CLI ignores the restrictions.

**Minimal remediation:** Distinguish settings supplied, options available, effective metadata checked, and behavior tested in the security table and policy record. Describe the MCP probe’s actual credential context. Credit the historical deterministic Codex write-denial probes as Tested for the recorded platforms and versions, separate from model-directed attempts. Preserve all existing controls and fail-closed checks; reserve enforcement claims for checks that demonstrate them.

### F3 — Low: the Copilot read-confinement claim exceeds the recorded per-model evidence

**Claims:** `docs/SECURITY.md:63` says that, on Linux with both models, `view` was denied for temporary-directory, home-directory, and repository-symlink targets. The `docs/STATUS.md:27` summary row says confinement of file reads and searches was “tested for every reviewer and backend”.

**Evidence:** The corresponding historical matrix in `docs/STATUS.md:503–518` records native Codex reading all three, native Claude and Copilot Claude being denied all three, but Copilot Codex **not attempting** the temporary and home reads. Only its symlink read is recorded as denied. The later Copilot 1.0.105 checks report all outside operations denied, but used `claude-sonnet-5.5` in both reviewer roles (`STATUS.md:215–220`); they do not establish the missing GPT attempts. The repository’s Copilot fixtures contain ordinary review streams and configuration probes, not those missing confinement results. For the `STATUS.md:27` summary, native Codex declined every search-confinement request for lack of search tools (`STATUS.md:74,132,169,530`). Those runs, like the unattempted Copilot Codex reads, are prompts sent, not tests that produced boundary evidence.

**Impact:** Readers selecting a backend/model combination are given stronger live coverage than the available record supports. This is a verification gap, not evidence that Copilot permits those reads. Sharing a CLI and settings is relevant supporting context but is not a recorded attempted denial for the other model.

**Minimal remediation:** Correct the SECURITY.md table and the `STATUS.md:27` summary to distinguish denied, not attempted, and unverified cases. Obtain and retain the missing attempted-operation evidence when extending the live matrix in `plan.md` section 8; do not count a model declining an operation as enforcement.

### F4 — Low: the web-risk comparison overstates confidentiality and audit coverage without web tools

**Claims:** `docs/SECURITY.md:88–89` says a manipulated reviewer without web tools “can only write a bad document.” Lines 95–100 contrast missing web evidence with file contents being in the audit record.

**Evidence:** The same document correctly states that inspected content reaches model providers (`:29–33,127`) and that native Codex can read outside the repository (`:41,46`). Thus manipulation can cause additional readable information to reach a provider even without web tools. That exposure is already documented elsewhere; it is not a newly discovered vulnerability.

Duo also does not independently archive the repository files inspected. `CLIAdapter.__call__` captures what the CLI emits (`src/duo/adapters.py:399–443`), and `RunStore.snapshot` saves the document under review (`src/duo/storage.py:167–168`). Native Claude’s recorded success envelope, `tests/fixtures/claude-2.1.296/result-approve.json`, contains the answer and usage but no successful file-read transcript. `plan.md` section 2 already recognizes this audit limitation. Codex and Copilot logs can contain tool output, but this is not a guarantee of complete source-file snapshots.

**Impact:** Users could incorrectly infer that disabling web prevents disclosure beyond the generated document, or that the audit can reconstruct every inspected file. Both assumptions matter when assessing an injected review or investigating what information was exposed.

**Minimal remediation:** Explain that web tools add search-provider and arbitrary-URL disclosure channels to the existing model-provider exposure. Describe both file and web evidence as dependent on emitted CLI logs, with explicit backend-specific omissions. Keep the planned Claude audit improvement, without promising complete file or page archives.

### F5 — Low: native fixture recording does not reproduce the restricted preflight environment

**Claim:** `scripts/record_fixtures.py:3–4` describes its probes as running “exactly as preflight does.” Restricted native probe and version-check environments are part of the security claims (`docs/SECURITY.md:44,55`).

**Evidence:** The recorder’s native subprocess helper defaults to `env=None` (`scripts/record_fixtures.py:92–121`), inheriting the complete parent environment. Its Codex MCP probe explicitly copies `os.environ` and changes only `CODEX_HOME`. Production native probes and version checks instead use `reviewer_environment` (`src/duo/adapters.py:252–266,285–286`; `src/duo/policy.py:63–67`). Copilot fixture probes already use `copilot.environment`.

**Impact:** A maintainer refreshing native fixtures can give the CLI unrelated credentials, provider overrides, or runtime injection settings such as `NODE_OPTIONS` that a normal Duo review drops. The resulting probe fixtures may also describe a different effective configuration. This is a tooling exposure and reproducibility discrepancy, not a bypass in the production reviewer environment; no actual disclosure was observed.

**Minimal remediation:** Use the same native environment builder for fixture probes, applying the temporary `CODEX_HOME` on top of it. Add an environment-capture regression check so fixture recording and production preflight cannot silently diverge again.

### F6 — Low: the documented offline test command is wrong, and a root invocation can falsely succeed with zero tests

**Claim:** `docs/SECURITY.md:170` gives `python scripts/run_tests.py` “from `tests/`.”

**Evidence:** There is no `tests/scripts/run_tests.py`. The script’s own instructions correctly say `cd tests && python ../scripts/run_tests.py` (`scripts/run_tests.py:4–6`). Running the displayed script path from the repository root instead discovers from `.` (`:19`) and does not reject an empty suite (`:21–24`). Read-only execution of `unittest.TestLoader().discover('.').countTestCases()` at this HEAD returned zero (`tests/` has no `__init__.py`, so root discovery does not descend into it). With LangGraph installed, that empty successful result would produce exit 0. CI uses the correct working directory, so this does not show that CI skipped its tests. README’s own command (`README.md:592`, `discover -s tests`) is correct.

**Impact:** Someone reproducing the security evidence can encounter a missing script or mistake a zero-test success for validation of the protections.

**Minimal remediation:** Correct the documented command, make the runner select the intended test directory independently of the caller’s working directory, and reject zero discovered tests while retaining failure-on-skip behavior.

## Related trust claims checked

- **Two approvals of the same document:** `workflow.py:106–135` clears approvals on every revision, requires both reviewer identities, and records the document hash. `WorkflowTests.test_draft_then_two_explicit_approvals`, `test_revision_invalidates_earlier_approval`, and the acceptance matrix exercise this. This establishes agreement mechanics, not correctness or security. Distinct identities do not enforce distinct model families; the same-model Copilot limitation is already recorded in `plan.md` section 5 and `STATUS.md:466–477`.
- **Refusal of untested CLI versions:** `policy.py:95–125` rejects versions outside the declared ranges unless explicitly allowed. Policy/Copilot tests verify refusal and experimental labeling. These are compatibility ranges, including later patches within a supported minor, not evidence that every accepted patch was exercised live. Allowing an untested version does not remove the control probes.
- **Audit record of every review attempt:** `workflow.py:58–60,78–81,125–136` records attempts, failures, accepted decisions, and hashes; `adapters.py:391–409` creates a fresh attempt directory and records command/raw streams. Acceptance tests cover malformed responses, stale-response prevention, nonzero exits, and audit failure not returning agreement. The record is useful local evidence, not an immutable ledger, a resumable checkpoint, or a complete repository snapshot.
- **Output/storage/input limits and process cleanup:** `adapters.py:30–82,370–383` monitors captured streams and run usage, checks again after process exit, and kills the process group on monitored failure. `tests/test_acceptance.py:test_timeout_and_limits_kill_real_process_group`, `test_monitoring_error_stops_the_reviewer`, and the resource-limit tests support these protections. `read_input` bounds regular-file reads even after growth. README correctly says sampling can overshoot and excludes Copilot’s unpacked runtime; these are not hard disk quotas. F1 is a separate gap in local response-processing time. Aggregate prompt sizing is already an improvement item in `plan.md` section 3.
- **Cleanup boundaries:** `cleanup.py:runtimes`, `scan`, and `main`, plus `copilot.py:discard_runtime`, avoid following the tested intermediate symlinks and skip active locked runs. `tests/test_cleanup.py` and acceptance tests cover those regressions. No additional isolation guarantee is inferred from these cleanup checks.
- **CI, drift, and release evidence:** `.github/workflows/ci.yml` defines the documented OS/Python matrix, installed-artifact tests, newest-dependency job, and dependency audit. The drift workflow and `scripts/check_drift.py` compare configuration/help metadata without model calls. Release tooling defines clean-build/install checks, exact-commit CI gating, checksums, and draft attestations. This confirms the mechanisms described in STATUS.md, not that current remote jobs, published assets, or dependency vulnerability results were independently verified here. Drift probes cannot replace live enforcement checks.

## Remaining live verification

Retain the gaps already listed in `plan.md` section 8: Codex 0.164–0.166 on macOS and 0.167 on Linux; Copilot 1.0.103+ on macOS; Fable availability through Copilot; document modes through Copilot on macOS and with mixed pairs; and web access on macOS, with mixed pairs, and in other modes.

For security-specific evidence, retain attempted-operation records and distinguish requests, successful access, explicit denial, and no attempt. This applies especially to F3 (including Copilot with a GPT model in the Codex role, which `plan.md` section 5 also needs), authenticated managed-policy behavior, network enforcement, and native Claude’s missing tool transcript. `plan.md` sections 2 and 4 already provide the relevant audit and deterministic-boundary work. Historical deterministic Codex write denials in STATUS.md are useful evidence and should not be erased or described as nonexistent.

The new implementation priority is F1, ahead of or together with the `plan.md` section 3 context-file credential check that would reuse the affected patterns. The evidence and tooling corrections can be addressed without relaxing any current control or reopening the accepted baseline. Native Codex’s unrestricted reads, login-shell environment reintroduction, and the absence of an isolation profile remain explicitly documented risks, not newly discovered vulnerabilities.
