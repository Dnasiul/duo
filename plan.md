# Duo improvement plan

## Goal and scope

Improve Duo from release 0.4.6 while preserving the default document-mode protocol: two read-only reviewers; success only after both approve the same unchanged document hash; clearing every approval after a revision; a restricted reviewer environment; refusal of CLI versions outside the supported ranges by default; and an audit record of every attempt. Preserve the explicit experimental `--allow-untested-cli` exception and its mandatory control probes. Reviewer agreement is a signal, not proof of correctness.

Section 10 proposes a separately authorized build mode with one bounded implementer and one read-only reviewer. Section 13 proposes optional document-review panels that extend two-reviewer agreement to unanimity among a fixed roster of read-only reviewers. Neither changes the default document-mode protocol or silently grants document reviewers write access.

Writing or approving this plan authorizes no implementation, code change, release, credential distribution, push, or model call. Future release numbers below are proposed milestones, not publication commitments. The supported deployment remains one user, trusted repositories, and unmanaged CLI configuration. Existing owner decisions about that baseline and allowing native Codex with `--allow-web` remain in force.

This replaces the earlier improvement plan while retaining sections 1–8. Section 9 records the security self-review remediation shipped in 0.4.6. Sections 10–13 incorporate build mode, structured verdicts, persistent recovery, and reviewer panels. The older production-readiness plan remains available as `git show 918d2c5:plan.md`.

## 3. Context files and a combined prompt budget

Status: open; retained with F1 as a prerequisite. Effort: medium. Depends on section 9.1, completed in 0.4.6; independent of the isolation milestone.

Relevant files: `src/duo/cli.py`, `src/duo/storage.py`, `src/duo/prompts.py` (`build_prompt`, `revision_diff`), `src/duo/models.py` (`Config`, `MAX_TEXT_BYTES`), `src/duo/workflow.py`, `src/duo/adapters.py`, `src/duo/copilot.py`, `tests/test_duo.py`, `tests/test_acceptance.py`, `tests/test_modes.py`, new `tests/test_context.py`, `README.md`, `docs/SECURITY.md`, `CHANGELOG.md`.

1. Add repeatable `--context-file PATH`. Use bounded regular-file reads through `read_input`, validate UTF-8, and reject the document under review, including aliases/hard links using the existing identity checks. Capture once at startup; do not reopen sources between turns or retries.
2. Before saving captured contents or starting reviewer processes, scan them with the repaired credential detector. For context there is no already-known-document exception: reject any recognized credential, naming only the file and credential kind. Document that this is best-effort detection, not clearance for sensitive material.
3. Store accepted exact bytes, labels, source paths, order, and content hashes in new context audit artifacts under the private run directory. Put the captured text into every review prompt as labeled untrusted material using the existing collision-resistant delimiters. Both reviewer roles receive the same captured context, although their evolving review history differs.
4. Enforce a documented 64 KiB aggregate context limit (a proposed cost control: roughly 16,000 extra input tokens on every call at about four bytes per token, varying with content and tokenizer).
5. Add a combined prompt budget as a new `Config` field with a new `--max-prompt-bytes` option. Count UTF-8 bytes after adding instructions, task, criteria, document, revision diff, selected history, context, retry feedback, delimiters, and backend wrappers, including Copilot's schema prefix. Check twice: (a) at startup, before any reviewer call, against the fixed parts (instructions, task, criteria, current document, context, wrappers), so an impossible run fails before spending calls; (b) before every subprocess call, against the full prompt. Reject overflow with a clear recorded error that names the largest sections; no silent truncation, and no retry of the same oversized prompt. A mid-run overflow (typically from a large revision diff) preserves the last accepted document and its snapshot so the user can rerun with a larger budget.
6. Compatibility: 0.4.6 accepts prompts far larger than any fixed small ceiling, and a full rewrite of a moderately large document produces a revision diff roughly twice the document's size. A low default (for example 256 KiB) would therefore reject runs that currently work, potentially partway through. Before release, measure the largest prompts in the supported examples and in recorded runs (including duo-on-duo plan reviews such as this one), then propose a default that accepts them with margin. If the proposed default would reject any input 0.4.6 accepts, it is an owner decision recorded in `CHANGELOG.md` as a compatibility change, not an engineering default. Byte limits are not exact token counts or a guarantee against model context exhaustion: CLI-added instructions, tool results, and output reserve also consume context.
7. Add a code-review example using a saved diff and test output. Test exact-byte capture, Unicode, invalid/nonregular inputs, document aliases, credential rejection before calls, aggregate context overflow, startup budget rejection before any adapter call, wrapper/history/diff/retry-induced mid-run overflow with the last document preserved, the `--max-prompt-bytes` override, unchanged captures after source edits, and audit write failure.

Acceptance: both reviewers receive identical captured context throughout a run; the audit reproduces its supplied bytes and hashes; recognized credentials and oversized prompts never reach a reviewer call; a run whose fixed inputs exceed the budget fails before the first call. Errors preserve the last accepted document. The chosen default accepts every measured supported example and recorded run, or its rejection of previously accepted inputs is recorded as an owner-approved compatibility change. A bounded live example demonstrates the supported workflow. Separately inspected repository files remain mutable and are not snapshotted by this feature.

## 10. Build mode — bounded implementation and review of a fixed diff

Status: proposed, gated on isolation; not implemented by 0.4.6. Effort: large after feasibility, with a revised estimate when supported backend/platform combinations are known. Dependencies: sections 3 and 11 for captured inputs, prompt limits, and verdict identity; section 4's feasibility report and working enforcement for every claimed combination. A successful read-only isolation gate alone is insufficient: the bounded writable role requires its own tests. Section 2 supplies improved Claude audit coverage where applicable, with remaining transcript omissions explicit.

Relevant files: `src/duo/models.py`, `src/duo/cli.py`, `src/duo/workflow.py`, `src/duo/adapters.py`, `src/duo/copilot.py`, `src/duo/policy.py`, `src/duo/storage.py`, `src/duo/prompts.py`, proposed `src/duo/build.py`, new `tests/test_build.py`, `tests/test_isolation.py`, `tests/test_acceptance.py`, `docs/SECURITY.md`, `docs/RUNBOOK.md`, `docs/STATUS.md`, `README.md`.

Evidence motivating the proposal: the task records a manual loop on 2026-11-23, outside Duo, with Codex `gpt-6-astra` implementing and Claude `claude-opus-5-5` reviewing diffs against the plan's acceptance criteria. All four section 9 fix groups were approved in two review rounds each, the suite grew from 182 to 201 tests, and a second loop hardened the flaky timing test. This supports investigating the workflow; it is not evidence of shipped Duo build-mode enforcement or an automated audit contract.

1. Add an explicit opt-in build invocation with a fixed task, nonempty acceptance criteria, base commit, implementer/reviewer identities, allowed change paths, and required validation commands. Capture and hash those inputs before any agent call. Criteria, scope, roles, and required checks cannot be changed by either agent. Changing them requires a new run with empty approvals. Approving a plan never launches this mode automatically.
2. Start from an explicit clean Git base and create a controller-managed disposable checkout with no writable link to the user's working tree or shared Git metadata. Initially refuse dirty starting states, submodule changes, and other unsupported file types or layouts before calls. The approved object is the complete change from the pinned base to a frozen candidate: a versioned canonical manifest of sorted paths, additions/deletions, file types/modes, exact content hashes, base commit/tree identity, and resulting tree identity, plus the exact rendered diff and its SHA-256 hash. Include newly created files; never rely on tracked-only `git diff` or an abbreviated display. Binary changes must have an explicit supported representation and review policy or be refused, never omitted. Record symlink targets without following them.
3. Bind every approval to a controller-generated subject containing the base identity, candidate-manifest hash, diff hash, fixed task/criteria/context hashes, role configuration, and required-check specification and evidence hashes. The controller verifies these values rather than trusting hashes supplied by a model. Any candidate, base, fixed-input, or bound-evidence change invalidates all approvals. Recheck identity immediately before reviews and final agreement; no test or formatter may mutate the approved candidate unnoticed.
4. Define the two approvals explicitly. The implementer edits, then all writable agent processes are stopped and reaped; the controller freezes the candidate. Required checks run on a disposable copy of that exact candidate, with their results captured. The implementer then explicitly approves that frozen subject in a read-only finalization phase. The other agent independently reviews the same subject and returns approve, revise, or blocked. Producing code, claiming tests pass, or submitting a candidate is not approval. Success requires both roles' explicit approvals of the same unchanged subject, with required checks passing. A revision request returns control to the implementer and clears both approvals; a blocked decision stops for user input. Two approvals here mean implementer sign-off plus independent review, not two independent read-only reviewers or two repeated reviewer votes.
5. Enforce the implementer's write boundary at the OS/filesystem level: only declared paths in the disposable checkout and enumerated scratch/cache paths are writable. The original repository, unrelated files, credentials, fixed criteria, review snapshots, controller audit/checkpoint files, and Git administrative data remain unwritable. Disable hooks and undeclared MCP/tool launchers; retain restricted environments, CLI-version refusal, and mandatory experimental-version probes. Stop descendants before freezing. Test execution uses a separate bounded runner with declared scratch and network policy; arbitrary project scripts must not inherit host write access or reviewer credentials. Provider authentication must coexist with these boundaries as demonstrated by section 4. Unsupported combinations fail before implementation begins, without fallback to ordinary execution.
6. Audit every implementation, validation, and review attempt, including failures and interruptions: input and policy hashes, role/model/backend/CLI identities, timestamps, budgets, permitted paths, candidate manifests/diffs, emitted tool events and their coverage limits, command arguments, exit status, bounded stdout/stderr, evidence hashes, findings, decisions/reasons, approval invalidations, and final subject. Audit or snapshot failure prevents agreement. Apply bounded capture, credential handling, and prompt-budget checks; reject unsupported or oversized artifacts rather than silently dropping content. The result is an auditable patch/candidate and human-readable report alongside section 11's verdict. Applying it to the user's checkout, committing, merging, pushing, releasing, or deploying requires separate authorization.
7. Test multi-round fixes, explicit implementer sign-off, stale and forged hashes, criteria changes, new/deleted/renamed files, modes and symlinks, unsupported binaries/submodules, failed checks, mutation during tests/review, surviving subprocesses, external edits, out-of-scope writes, audit failure, and interruption. Obtain deterministic boundary evidence and a bounded live implementation/review run for each claimed combination. Initial build mode refuses panel and resume combinations; interrupted candidates remain available for inspection or a separately started fresh build run with empty approvals. Adding those combinations requires dedicated state and boundary tests, not implicit reuse of document recovery.

Acceptance: success identifies one reproducible diff/candidate and fixed criteria with two explicit role-bound approvals and passing required checks. Every change invalidates approvals. Reviewer and implementer-finalization phases are read-only; implementation writes stay within the enforced disposable boundary. Unsupported combinations and failed gates refuse safely. Document modes retain their existing read-only behavior, and no agreement automatically applies or publishes code.

## 11. Structured verdicts and findings for external gates

Status: proposed. Effort: medium, including schema design, adapter validation, fixtures, and a reference CI consumer. Dependencies: section 3's captured-input and prompt-budget support; coordinate terminal parsing with section 2. Initial delivery covers document modes; section 10 adds the explicitly typed diff subject. This is distinct from the existing `--json` summary.

Relevant files: `src/duo/models.py` (`SCHEMA`, `validate_payload`, `validate_review`, `Turn`, `State`), `src/duo/cli.py`, `src/duo/workflow.py`, `src/duo/storage.py`, `src/duo/prompts.py`, `src/duo/adapters.py`, `src/duo/copilot.py`, new versioned schema files, new `tests/test_verdicts.py`, `tests/test_fixtures.py`, `tests/test_modes.py`, `examples/`, `README.md`, `docs/RUNBOOK.md`.

1. Publish a JSON schema for a `verdict.json` artifact written alongside the human-readable document/report, with `schema_version`, run identity, completion state, mode, typed reviewed subject and hashes, fixed-input hashes, agreement rule and roster, per-role decisions/approval bindings, findings, and audit references. Distinguish completed agreement, blocked, limit, error, and interrupted/incomplete states. A schema-valid empty findings list is not agreement. The verdict is generated from validated workflow state, never inferred from prose or a partial CLI stream.
2. Each finding has an immutable ID, severity from a documented ordered enum (`info`, `low`, `medium`, `high`, `critical`), title/description, status (`open`, `resolved`, `dismissed`), reporting role and attempt, and location. Locations identify the versioned subject plus repository-relative path and line/range where meaningful; document sections and diff old/new sides are supported. Whole-document or non-line findings use an explicit subject-level location and explanation rather than invented line numbers. Validate location shape and bounds where the captured subject permits it.
3. Duo allocates run-scoped finding IDs and requires later updates to reference them. Preserve IDs through revisions and recovery; record first/last-seen subject hashes, changed locations, and disposition evidence. IDs are not promised to match across independent runs. Duplicate reports retain their own IDs with optional explicit links; do not silently merge distinct concerns. Unknown IDs, duplicate updates, unsupported severities, malformed locations, or invalid dispositions fail validation. Every new field remains subject to size limits and credential checks.
4. Findings persist until explicitly resolved or dismissed with a reason and subject-bound evidence by their reporting role. Omission in a later response does not close a finding. Other roles' dissent remains separately open. The final aggregate retains unresolved findings from all roles, marking sightings on earlier subjects; a completed final review must explicitly reconcile that role's existing open findings against the final subject. A revision response's findings belong to the inspected input subject, not an approval of its proposed replacement. The controller never edits the approved document merely to align it with the findings artifact.
5. Version the exported schema independently from package releases. Freeze field meanings, severity ordering, ID scope, subject hashing, and completion semantics within a major schema version; additive optional fields use minor versions, while incompatible changes require a major version and migration notes. Ship schemas and valid/invalid fixture examples. Negotiate or explicitly select the new model-response schema and update every supported adapter; keep existing CLI summary behavior compatible or document an explicit versioned option. Do not require consumers to parse `reason` text.
6. Provide a reference CI gate for a changed plan or protocol document. It passes only when the artifact uses a supported schema, is complete, records the configured agreement rule, matches the expected current subject and task/criteria hashes, and has no open finding at or above a configured severity threshold. Missing, stale, malformed, incomplete, blocked, or non-agreed results fail closed. Keep gate failure distinct from Duo's existing run exit codes. Generate or obtain the artifact in the trusted CI execution path; hashes bind content but are not signatures or protection against an actor rewriting both artifact and content.
7. Atomically publish the final verdict only after its corresponding state, snapshots, and audit records are durable. Preserve attempt-level structured responses, including failures, and clearly label intermediate artifacts. Test severity thresholds, stable IDs across moved locations/revisions, omitted unresolved findings, differing role opinions, stale subjects, schema compatibility, partial writes, unsuccessful terminal envelopes, and a CI example that fails both for missing agreement and a threshold finding.

Acceptance: documented schemas and fixtures let an external consumer decide agreement and finding thresholds without parsing prose. A reference CI gate accepts a valid current agreement and rejects stale, absent, incomplete, incompatible, or threshold-failing artifacts. Findings retain traceable identities and dispositions, and human-readable output and existing document approval semantics remain intact.

An interrupted attempt with no durable accepted response is recorded as interrupted and consumes its reserved attempt; another call is a new audited attempt and may incur cost again.
7. Extend cleanup and retention so recovery artifacts remain coherent: active runs stay locked; paused recoverable runs are identified in previews and protected from routine pruning unless explicitly selected for abandonment/deletion. Runtime caches may be rebuilt without deleting required snapshots/checkpoints. Test process death at each attempt/validation/snapshot/publication/checkpoint boundary, torn or missing files, interrupted calls, disk-full errors, concurrent resume, stale documents, consumed retries/deadlines, policy refusal, cleanup, and recovery after one prior approval and after a revision. Demonstrate an interrupted multi-turn run continuing from its saved document/history while requiring fresh agreement.

Acceptance: a supported interrupted document run resumes from a verified durable boundary without discarding its committed work or resetting budgets. No crash invents a review, repeats a committed publication, hides an attempt, or reuses an approval. Corrupt or incompatible state fails before calls; every resumed run records its lineage and approval reset. Current rerun behavior remains available, and existing audit-only runs are clearly distinguished from recoverable runs.
